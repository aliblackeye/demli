# ADR 0009 — Localization (i18n) & System Message Tokens

**Status:** accepted — shipped; TR/EN catalogues are live and key parity is test-enforced
**Date:** 2026-07-09

## Context

The app currently mixes languages with no single source of truth:

- UI chrome (desktop renderer, mobile) is mostly **English**
  (`friendlyErrorMessage`, auth notices, buttons).
- The desktop auto-updater and its blocking "forced update" overlay are
  **Turkish** (`apps/desktop/src/main/auto-update.ts`, e.g.
  `"Güncelleme indirilemedi. İnternet bağlantınızı kontrol edin."`).
- Server "system" messages are written to the database in **Turkish**
  (`apps/api/src/lib/system-messages.ts`: `` `${displayName} sunucuya katıldı` ``).

The founder's requirement: the app opens in the **device language**, the user
can change it from settings, and the choice is **consistent across every
platform** (desktop + mobile). No more English/Turkish salad.

Two structural problems block a clean fix:

1. There is no shared place for translated strings. Desktop and mobile are
   separate apps; duplicating catalogs guarantees drift.
2. System messages bake human-language text into **persisted, broadcast**
   message rows. A row written in Turkish stays Turkish forever, ignores the
   viewer's language, and — worse — embeds the author's `displayName` at write
   time, so a later rename leaves the old name frozen in history.

Constraints that shape the solution:

- **No native modules on mobile.** `apps/mobile` pins `runtimeVersion: "1.0.0"`
  (fixed). Adding a native module (e.g. `expo-localization`) changes the native
  runtime fingerprint and would break OTA updates for already-installed APKs —
  an OTA bundle can only ship JS, not new native code. Device-language
  detection on mobile must therefore be **JS-only**.
- The shared transport package `@demli/client-core` (ADR 0002) is
  deliberately React-free and RN-safe. i18n is React-facing, so it must live in
  its **own** package, not be bolted onto client-core.
- Both apps are React (desktop React 18, mobile React Native 19), so a
  React-based i18n binding works on both.

## Decision

### 1. Library: i18next + react-i18next

Use **i18next** (core) with **react-i18next** (React binding), shipped as a new
workspace package `@demli/i18n`.

Rationale:

- One engine runs on **both** desktop (React DOM, bundled by Vite) and mobile
  (React Native, bundled by Metro) with identical catalog format and the same
  `useTranslation()` / `Trans` API. No platform-specific i18n code.
- Pure JS, zero native dependencies — satisfies the mobile OTA constraint.
- Namespaces, interpolation, pluralization, and language detection are built
  in; TypeScript key-safety via `CustomTypeOptions` module augmentation.
- Framework-agnostic core: `createI18n()` initializes a plain i18next instance
  (usable in tests / Node) and attaches the React binding via
  `initReactI18next`.

**Alternatives considered** (see below): `react-intl` (FormatJS), `lingui`,
`expo-localization`, and a hand-rolled dictionary.

### 2. Package shape — `@demli/i18n`

```txt
packages/i18n/src/
  config.ts          SUPPORTED_LOCALES ["en","tr"], DEFAULT_LOCALE "en",
                     NAMESPACES ["common","desktop","mobile"], isSupportedLocale
  detect.ts          detectDeviceLocale(): Locale  (JS-only, safe fallback "en")
  storage.ts         LocaleStorage adapter interface + createMemoryStorage()
  resources.ts       assembles JSON catalogs into the i18next resources object
  create-i18n.ts     createI18n({ lng?, storage }) + setLocale()
  system-messages.ts resolveSystemMessage(content, displayName, t) + tokens
  i18next-env.ts     i18next CustomTypeOptions augmentation (type-safe keys)
  index.ts           public surface (+ re-exports useTranslation/Trans/Provider)
  locales/{en,tr}/common.json    shared: errors, buttons, system templates
  locales/{en,tr}/desktop.json   SKELETON ({}) — filled by wave I2
  locales/{en,tr}/mobile.json    SKELETON ({}) — filled by wave I3
```

The package owns **only** the skeleton + the `common` namespace in this wave.
`desktop`/`mobile` catalogs are created empty and wired into `resources` and
`NAMESPACES`; the I2/I3 waves fill the JSON with no plumbing changes.

### 3. Namespace strategy

Three namespaces, split by ownership to prevent cross-wave merge conflicts:

- **`common`** — anything shared by both platforms: error messages (network /
  server / session-expired / invite-expired…), generic buttons (cancel, save,
  retry, leave…), and **system-message templates**. Owned here (this wave).
- **`desktop`** — strings only the Electron app renders (updater overlay, tray,
  window chrome, desktop-only settings). Owned by wave **I2**.
- **`mobile`** — strings only the React Native app renders. Owned by wave **I3**.

Rule of thumb for contributors: **if two platforms could show the same string,
it goes in `common`.** Only genuinely platform-specific copy goes in `desktop`
/ `mobile`. `common` is the default namespace, so shared code calls
`t("errors.network")` with no prefix; platform code uses `t("desktop:…")`.

**Key naming convention** (documented for I2/I3):

- Nested, dot-separated, lowerCamel leaves: `errors.network`,
  `buttons.retry`, `system.member_joined`, `settings.language.title`.
- Group by feature/area, not by screen, so keys are reusable.
- Interpolation uses i18next double braces: `"{{name}} joined the server"`.
- No sentence-fragment concatenation — one key per full user-visible string.
- System-message templates live under `system.<token>` where `<token>` matches
  the persisted `@sys:` token exactly (see §5).

### 4. Device-language detection (JS-only, per platform)

`detectDeviceLocale()` reads the raw locale from whichever source exists, then
normalizes to a supported locale (primary subtag, lowercased) with a safe
fallback to `"en"`:

- **Desktop (Electron renderer / web):** `navigator.languages[0]` →
  `navigator.language`.
- **Mobile (React Native / Hermes) & Node:**
  `Intl.DateTimeFormat().resolvedOptions().locale`. Hermes ships Intl, so this
  is JS-only — **no `expo-localization` or any native module**, which is a hard
  constraint because `runtimeVersion` is frozen at `"1.0.0"` and adding native
  code breaks OTA delivery to installed APKs.

Resolution order at startup (`createI18n`): explicit `lng` argument (a value
the app already resolved) → persisted user choice from `storage` → detected
device locale → `"en"`.

Persistence is via a small `LocaleStorage` adapter (`get`/`set`, sync **or**
async) that each app provides — desktop wraps `localStorage`, mobile wraps
`AsyncStorage`. The package never imports either, so it stays native-free.
`createI18n` persists on every `changeLanguage`, so "user changes it in
settings" is one call: `setLocale(i18n, storage, "tr")`.

### 5. System messages become stable tokens

`postMembershipSystemMessage` stops writing human language. It writes a
**stable, language-neutral token** as the message `content`:

```txt
@sys:member_joined
@sys:member_left
```

Crucially, the token carries **no display name**. The client already has the
message's `authorId`; it resolves the current `displayName` itself at render
time. This is strictly more correct than the old scheme: renaming a user
updates every past system message, and the persisted `content` never has to
change.

Client rendering uses `resolveSystemMessage(content, displayName, t)` from
`@demli/i18n`:

- `@sys:member_joined` → `t("common:system.member_joined", { name })`.
- **Unknown `@sys:` token** or **plain text** (legacy Turkish rows written
  before this change) → returned **verbatim**. This is the backward-compat
  contract: old data keeps rendering exactly as it did, so no data migration is
  required.

The API test suite asserts the token content instead of the Turkish sentence.

**Why not migrate old rows?** They are best-effort notifications, not user
data; a migration adds risk for zero product value. The verbatim fallback makes
them harmless.

## Consequences

- One catalog format, one engine, one `useTranslation` API across desktop and
  mobile. New strings land in `common` (shared) or a platform namespace.
- Mobile stays OTA-safe: detection and the whole i18n stack are pure JS.
- System-message rows are now language-neutral and rename-correct; every viewer
  sees them in **their** language. Legacy Turkish rows still render (verbatim).
- Type-safe `t()` keys via i18next module augmentation catch typos at compile
  time. Empty `desktop`/`mobile` namespaces mean their keys type-error until I2
  / I3 add them — an intentional guardrail.
- New runtime deps: `i18next`, `react-i18next` (both pure JS). `react` is a
  peer (apps provide the singleton). No native module is added.
- Downstream waves: **I2** (desktop) wires `createI18n` with a `localStorage`
  adapter, adds an `I18nextProvider`, moves the updater/overlay Turkish strings
  into `desktop`/`common`, and adds a language setting. **I3** (mobile) does the
  same with an `AsyncStorage` adapter and fills `mobile`. Both consume
  `resolveSystemMessage` in their message renderers.

## Alternatives considered

- **react-intl (FormatJS)** — ICU MessageFormat is powerful, but the API is
  heavier (`<FormattedMessage>` / `intl.formatMessage` with message
  descriptors), RN ICU needs care, and catalog compilation adds a build step.
  i18next's runtime catalogs are simpler for a two-language MVP and share
  effortlessly between Vite and Metro.
- **Lingui** — great DX and macro-based extraction, but the Babel macro +
  compile step is extra tooling on top of two different bundlers (Vite + Metro),
  and the payoff (message extraction at scale) is not needed for two languages.
- **expo-localization for detection** — the ergonomic choice on Expo, but it is
  a **native module**. With `runtimeVersion` frozen at `"1.0.0"`, adding it
  changes the native fingerprint and breaks OTA updates for installed APKs.
  Rejected; `Intl.DateTimeFormat().resolvedOptions().locale` (Hermes, JS-only)
  gives the same information without native code.
- **Hand-rolled dictionary (`t = (key) => catalog[locale][key]`)** — zero deps,
  but we would reimplement interpolation, pluralization, namespaces, fallback,
  and React re-render-on-change. Not worth it versus a mature, tiny library.
- **Keep system messages as human text, translate on write** — cannot serve
  different viewers different languages from one persisted row, and freezes the
  author's name at write time. Tokens decouple storage from presentation.
